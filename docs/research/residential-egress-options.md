# Residential Egress Options for `ytt` (YouTube Transcript MCP)

**Date:** 2026-06-14
**Problem:** `ytt` is a remote MCP server that runs as a public HTTPS service (registered as a Claude custom connector). The actual YouTube fetch uses `yt-dlp`. YouTube blocks datacenter IPs (AWS/GCP/Azure/Hetzner/Rackspace) for transcript fetching, and 2026 bot detection (PoToken / BotGuard) has made **IP reputation the binding constraint** — not the extraction code. The MCP control plane can live in a k8s cluster, but the YouTube fetch itself must exit from a **non-datacenter IP**.

---

## Summary

The hard constraint: **the IP that talks to YouTube must not look like a datacenter.** Everything below is just a different way to obtain such an IP. The cleanest split is:

- **Buy the IP** (rotating residential proxy service) — zero hardware, pay per GB, the path the `youtube-transcript-api` author actually ships and recommends.
- **Own the IP** (self-hosted residential box / Tailscale exit node on a home line / the Pixel 6 over ADB) — free-ish marginal cost, but you must *already have a residential or cellular line you control*, and the user's listed infrastructure (Hetzner, Rackspace Spot) is **all datacenter** — none of it qualifies.

For a few transcripts/day, the pragmatic winner is **Webshare rotating residential proxies** (~$3.50/mo for 1 GB, which is thousands of transcripts since transcript payloads are tiny KB-scale text). It's a 3-line config change, no hardware, no home-line dependency, and it is the option the upstream library is built around. The phone-as-egress trick is genuinely viable as a free fallback but is janky and fragile.

---

## Option 1 — Rotating Residential Proxy Services (buy the IP)

**How it works.** Your `yt-dlp` request goes out through a provider's pool of real consumer-ISP IP addresses (Comcast, Verizon, etc.), rotating per request or per session. YouTube sees a Comcast subscriber, not Hetzner.

**Why it beats datacenter and how it differs from static residential:**

| Type | What YouTube sees | Detectability | Fit for `ytt` |
|------|-------------------|---------------|---------------|
| **Datacenter** | ASN owned by AWS/Hetzner/OVH | High — datacenter ASNs are on public blocklists; 20–40% success on anti-bot sites, blocked after as few as 5–10 fetches | ✗ this is the thing we're escaping |
| **Static residential / ISP** | One fixed consumer-ISP IP you keep | Low *until* that single IP burns, then you're stuck | OK but a burned IP = manual rotation |
| **Rotating residential** | A different real consumer IP per request/session | Lowest sustained — burning one IP just rotates to the next | ✓ best for unattended low-volume |
| **Mobile/cellular** | Carrier CGNAT IP shared by thousands | Lowest of all (collateral-damage protection) but priciest | ✓ overkill for personal volume |

**ASN-detectability.** Datacenter ASNs are trivially fingerprinted and widely blocklisted; residential ASNs belong to consumer ISPs and blend with normal traffic. This is the entire reason the `youtube-transcript-api` author "found Webshare to be the most reliable and have therefore integrated it into this module" — there's a first-class `WebshareProxyConfig` in the library. **Important upstream caveat:** the library docs warn you must buy the **"Residential"** product, *not* "Proxy Server" or "Static Residential," or it won't behave as the integration expects.

**Surviving 2026 PoToken detection.** PoToken / BotGuard binds a token to the session/video and is generated by JS challenge — but in practice the *binding constraint reported across yt-dlp issues remains IP reputation*, not token generation (yt-dlp handles tokens via `bgutil-ytdlp-pot-provider` and similar). A clean residential IP is what flips "Sign in to confirm you're not a bot" off. Rotating residential survives best because a flagged IP is simply rotated away; no provider *guarantees* immunity (YouTube can always block a specific proxy IP), but the pool model makes that self-healing.

**Rough pricing (per-GB, 2026):**

| Provider | Residential price | Notes |
|----------|-------------------|-------|
| **Webshare** | **~$1.40–$2.80/GB** (1 GB ≈ $3.50/mo with current 50% promo; $1.12/GB at top yearly tiers); free tier 10 proxies / 1 GB | Budget tier; the community/library default for `youtube-transcript-api`; lowest setup friction |
| **Decodo (ex-Smartproxy/"Decodo")** | $2.00–$3.75/GB | Best value at mid-volume (≥1000 GB); good docs |
| **Oxylabs** | ~$3.87/GB (13 GB entry) | Enterprise IP quality |
| **Bright Data** | ~$10.50/GB | Largest pool, enterprise features, priciest |

**Cost for low-volume personal use.** Transcripts are plain text — kilobytes each. A few transcripts/day is *megabytes/month*, far under 1 GB. **Realistic cost: the $3.50/mo Webshare 1 GB plan, or even the free 1 GB tier**, will cover personal use indefinitely.

**Pros:** zero hardware; no home-line dependency; 3-line code change; self-healing rotation; the supported/blessed path.
**Cons:** recurring (small) cost; you're trusting a third party with your traffic; no provider guarantees zero blocks.

**Pragmatic default: Webshare rotating residential.**

## Option 2 — Self-Hosted Residential Worker Box (own the IP)

**Architecture.** Split the system: the MCP control plane (the HTTPS connector endpoint) stays in a cluster; a tiny worker process runs `yt-dlp` on a machine sitting behind a *residential* internet connection. The control plane calls the worker over **Tailscale** (a private `100.x` address or a `ts.net` MagicDNS name), the worker fetches from YouTube over its residential WAN, and returns the transcript text. Tailscale means the worker needs **no public ingress / port-forwarding** — it dials out only.

**The catch — where do you get the residential IP?** This is the whole problem, and the user's listed infra does **not** solve it:

- **Hetzner is NOT residential.** It's a dedicated server in a datacenter; its IP is on the exact datacenter blocklists we're escaping. Running the worker there is pointless.
- **Rackspace Spot clusters are datacenter.** Same disqualification.

So "self-hosted" only works if the user has (or adds) a real consumer line:
- A box at **home/office** on Comcast/Verizon/etc. (a spare PC, a Raspberry Pi, a NAS) → ideal, free marginal cost, full control.
- The **Pixel 6's** connection → that's Option 4.
- A **home-line a friend/relative hosts** → works but socially awkward and you don't control uptime.

**Pros:** no per-GB cost; full control of the IP; no third party sees your traffic; pairs naturally with the existing Tailscale mesh.
**Cons:** requires a residential line + always-on hardware you actually own; single static IP can burn (no auto-rotation); home uptime/power/ISP outages become your reliability ceiling; if the user has no home box this option simply doesn't exist for them.

## Option 3 — Tailscale Exit Node on a Residential Connection

**How it works.** Instead of a dedicated worker, advertise a device on a residential line as a **Tailscale exit node** (`tailscale up --advertise-exit-node`, approve in admin console). The cluster pod/worker selects that exit node, so *all* its outbound traffic — including the `yt-dlp` fetch — egresses from the home ISP. YouTube sees the residential IP. This is a well-trodden Tailscale pattern (route all traffic through a home node), and it works fine behind CGNAT/Starlink because Tailscale only needs outbound connectivity, no port-forwarding.

**Relationship to Option 2.** It's the same "own the IP" idea but at the *network* layer instead of an app-level worker call. Pro: no custom worker code — the existing fetch just runs in the cluster and is transparently routed. Con: it routes *all* selected traffic through home (coarser than a per-request worker call), and you'd typically scope it so only the fetch path uses the exit node.

**The same catch.** You still need a residential line with an always-on Tailscale device. Hetzner/Rackspace nodes can be exit nodes, but they're **datacenter exit nodes** — useless here. There is no residential line in the user's stated inventory except the Pixel 6.

**Pros:** elegant, no app changes, reuses the existing Tailscale-everywhere mesh; works behind CGNAT.
**Cons:** requires the residential line (the binding catch); single IP, no rotation; home device must stay up; coarser traffic control than a worker.

## Option 4 — Phone-as-Egress (Pixel 6 over ADB / Tailscale)

**The idea.** The user already has a Pixel 6 connected via **ADB over Tailscale** (`100.88.10.113`). The phone routes through a **mobile carrier** (cellular) or a home Wi-Fi network. Could the `yt-dlp` fetch be tunneled out through the phone so YouTube sees a carrier/residential IP?

**Is a cellular IP treated like residential?** Effectively **yes — arguably better.** Mobile carriers use **CGNAT**, where hundreds-to-thousands of real phone users share one public IP. Blocking that IP would collateral-damage many legitimate users, so anti-bot systems are *more lenient* toward mobile IPs than even residential ones (mobile-proxy vendors quote ~95%+ detection resistance vs ~70% for plain residential — vendor marketing, but the CGNAT logic is real). So a carrier IP is a strong egress identity for YouTube.

**Can you actually tunnel through it?** Mechanically possible, several ways, all hacky:
- **Tailscale on the phone as an exit node** — install the Tailscale Android app, advertise the phone as an exit node, route the cluster's fetch through it. This is the cleanest version (no ADB hackery) and gives you the carrier IP directly. *This is the realistic implementation.*
- **ADB reverse/forward tunneling** — proxy traffic through `adb` to a SOCKS/HTTP proxy app running on the phone. Far more brittle; ADB is meant for debugging, not as a production egress path.

**Honest assessment — how janky is this?**
- The phone is **not a server**: Android kills background apps, Doze mode suspends networking when idle, the screen-off state can drop the Tailscale tunnel, and the device reboots/moves/loses signal.
- The environment's own notes say the ADB **connect port changes on reboot** and reconnection sometimes needs the user to read a new port off the phone — i.e. it's **not reliably unattended**.
- Per the same notes the Pixel 6 **has no SIM** in some configs (`feedback_adb_no_sim`), so it may currently be **Wi-Fi-only** — meaning it'd egress from the *home/office Wi-Fi residential IP*, not a cellular one. Either is non-datacenter and fine for YouTube, but it changes the story (and if it's on the same LAN as nothing residential, verify).
- The phone is **shared** — other agents drive it via ADB; using it as a always-on egress conflicts with interactive use and the "don't send concurrent input" rule.

**Verdict.** Viable as a **free, zero-extra-cost fallback for genuinely low personal volume**, *if* the phone is already always-on, charging, and on a stable network with Tailscale exit-node mode (not ADB tunneling). Failure modes: Doze drops the tunnel, reboot changes ADB port, no-SIM means Wi-Fi-only, contention with other agents, and a single IP that can still burn. **Don't build the primary path on it** — it's the "I refuse to pay $3.50/mo and already have the phone up" option.

## Recommendation Matrix

| Option | Monthly cost | Setup effort | Reliability (unattended) | Personal low-volume fit | Needs a residential line you own? |
|--------|-------------|--------------|--------------------------|-------------------------|-----------------------------------|
| **1. Webshare rotating residential** | **~$0–3.50** | **Low** (3-line config; library-native) | **High** (self-healing rotation) | **Best** | No |
| 1b. Decodo / Oxylabs / Bright Data | $5–$30+ | Low | High | Overkill (priced for scale) | No |
| 2. Self-hosted residential worker | ~$0 (hardware/power) | Medium (worker + Tailscale + a home box) | Medium (home uptime; single IP) | Good *if* you have a home box | **Yes** |
| 3. Tailscale exit node on home line | ~$0 | Medium (advertise/approve exit node) | Medium (home uptime; single IP) | Good *if* you have a home line | **Yes** |
| 4. Pixel 6 phone-as-egress | ~$0 | Medium-High (phone exit node; fragile) | **Low** (Doze, reboots, port drift, no-SIM, shared) | Fallback only | Sort of (phone's own line) |

**Note:** Options 2 and 3 are *disqualified by the user's current inventory* — Hetzner and Rackspace are datacenter, and the only residential/cellular line on hand is the Pixel 6 (Option 4). To use 2 or 3 the user must add a real home box/line.

### Explicit recommendation

- **Low-volume personal use (a few transcripts/day): use Webshare rotating residential proxies.** Start on the free 1 GB tier, upgrade to the $3.50/mo 1 GB plan if you exhaust it (you almost certainly won't — transcripts are KB-scale text). It's the simplest thing that works, requires no hardware, has no home-line dependency, and is the exact integration the upstream `youtube-transcript-api` ships. Put the proxy on the fetch worker; the MCP control plane stays in the cluster as planned.
- **If you flatly won't pay and the Pixel 6 is already always-on, charging, and on a stable network:** run Tailscale exit-node mode on the phone (not ADB tunneling) as a free fallback — accept the jank.
- **If you later want a robust free path:** stand up a small **home box on a residential line** as a Tailscale exit node (Option 3) or a `yt-dlp` worker (Option 2). This is the right answer *only once you have a residential line you control* — which today you do not, apart from the phone.
- **Higher volume / multi-channel / many users:** move up to **Decodo** for better $/GB at scale, or **mobile proxies** if YouTube tightens further and even residential starts burning. Bright Data/Oxylabs only if you need enterprise pool size/SLAs.

**The simplest thing that works:** point the `ytt` fetch worker at Webshare residential via `WebshareProxyConfig` and move on.
